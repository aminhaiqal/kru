# M2 — The durable mailbox

Implemented from pages 26–31 of the
[project plan](Kru%20%E2%80%94%20Project%20Plan%20%26%20Milestones.pdf).
M2 stores deliveries and transitions their states. It does not start a provider
or execute a turn. Existing `kru chat` remains the direct M1 chat path.

## Try it

```sh
bun run dev -- init
bun run dev -- agent create reviewer --provider fake
bun run dev -- agent create coder --provider codex --cwd .
bun run dev -- agent list
bun run dev -- send reviewer "review the latest commit" --idempotency-key review-1
bun run dev -- queue reviewer
# <delivery-id> queued user "review the latest commit"
bun run dev -- cancel <delivery-id>
bun run dev -- retry <delivery-id>
```

`send reviewer,coder "review this"` creates one message and two independent
deliveries. Agent arguments accept exact ids or unique names. The library accepts
ids only. Agent creation stores configuration without starting any provider or
requiring credentials.

Run `kru init` once at the project root. Commands search upward from the working
directory for the nearest `.kru/`, then open its `kru.sqlite`. Missing projects
or missing databases fail with an initialization hint; they do not silently
create a mailbox. `init` reuses an existing ancestor project, including its data.
`KRU_DB` overrides discovery; `--db <path>` takes precedence over both. Explicit
paths are relative to the working directory and may create a database. This
resolution also applies to `new Store()` without an explicit path. `.kru/` is
already ignored by Git.
`agent create --cwd <path>` records an absolute workspace path in `config_json`.
Providers supported by the CLI are `fake`, `codex` and `claude`.

`queue` lists queued, starting and running deliveries in sequence order. Omit
`--lane` to list every lane, use `--main` for the main lane, or `--lane <id>` for
one side lane. `send` defaults to the main lane and also accepts `--lane`,
`--reply-to <message-id>` and `--expects-reply`. Use `--` before text that begins
with a dash. Queue output JSON-escapes message text so embedded newlines and
terminal controls do not break rows.

## Modules and port

- `src/store/db.ts`: SQLite opening, migrations and synchronous writer transactions.
- `src/store/migrations/001-initial.sql`: schema version 1.
- `src/agents/index.ts`: the minimal persistent agent registry.
- `src/mailbox/types.ts`: the `Mailbox` port, sender, delivery and receipt types.
- `src/mailbox/state.ts`: the single allowed-transition table.
- `src/mailbox/sqlite.ts`: the SQLite adapter, queue queries and notifications.
- `src/cli/mailbox.ts`: agent and mailbox commands.

Library entrypoints are `kru/store`, `kru/agents` and `kru/mailbox` in this
checkout's package exports. The package remains private and unpublished.

```ts
import { Store } from './src/store';
import { AgentRegistry } from './src/agents';
import { SqliteMailbox, type Mailbox } from './src/mailbox';

const store = new Store(); // discovers the initialized project or honors KRU_DB
try {
  const agents = new AgentRegistry(store);
  const reviewer = agents.resolve('reviewer') ?? agents.create({
    name: 'reviewer', provider: 'fake', config: { cwd: process.cwd() },
  });
  const mailbox: Mailbox = new SqliteMailbox(store);
  const receipt = mailbox.enqueue({
    sender: { kind: 'user' }, recipientIds: [reviewer.id], text: 'review this',
    idempotencyKey: 'review-1',
  });
  console.log(receipt, mailbox.listQueue(reviewer.id));
} finally {
  store.close();
}
```

The mailbox imports no provider implementation. M3 can depend on the `Mailbox`
interface, and M4 can replace the persistence adapter without changing callers.

## Persistence decisions

The database enables foreign keys, WAL, a 5-second busy timeout and
`synchronous=FULL`. The SQLite version is checked at startup; 3.35 or newer is
required. Local verification used SQLite 3.51.0. The transaction API follows
[Bun's SQLite documentation](https://bun.sh/docs/runtime/sqlite).

Each write acquires `BEGIN IMMEDIATE` before reading the state it will change.
`claimNext` selects the lowest queued `seq` for an exact agent/lane pair and
updates it with `WHERE id = ? AND status = 'queued'` under that lock. Every
transition checks the common transition table and requires one changed row.
Multiple connections or processes cannot claim the same delivery. Claiming
several deliveries in one lane is permitted; M3 owns the rule that only one
turn runs per lane through the database-backed batch design in
[M3 design decisions](m3-design.md).

Allowed transitions are:

| From | To |
| --- | --- |
| queued | starting, cancelled |
| starting | queued, running, failed, interrupted |
| running | completed, failed, interrupted |
| completed, failed, interrupted, cancelled | none |

The prose on page 28 explicitly allows a provider refusal before a turn starts
to end `failed`, although the page-27 diagram omits that arrow. The implementation
follows that prose. `completed` always requires a confirmed running turn.
`restore` is only for a start known not to have begun. An uncertain outcome must
be interrupted; no operation automatically retries it.

A retry creates a new queued delivery for the same immutable message, links
`retry_of` to the selected final attempt, and retains its recipient, lane, chain
and hop. The old attempt stays final. The new attempt gets a fresh id and seq,
with no turn id or error. `restore` instead retains the original seq. `seq` uses
`AUTOINCREMENT` so previously used queue positions are not reused.

One message may have several delivery rows. Its globally unique idempotency key
and SHA-256 request hash are stored in the same transaction as all deliveries.
The hash includes sender identity, sorted recipients, text, lane, reply target,
reply expectation and explicit chain. Omitted defaults are normalized. A replay
returns the original message and original delivery ids with `duplicate: true`,
even after restart or explicit retries. A different request under that key throws
`IdempotencyConflictError` and writes nothing. Duplicate recipient ids are refused.
Keys currently remain until explicitly removed; the agreed pre-v0.1 policy is a
30-day minimum retention, pinned while any attempt remains open. Expiry lookup and
pruning will arrive in a later migration, as specified in [M3 design decisions](m3-design.md).

Two small additions reconcile the sample SQL with the plan's core types:
`messages.sender_routine_id` retains routine identity, and `expects_reply` persists
the default-false reply flag. Chain id and nonnegative hop are present from v1.
Sender shape, statuses, JSON configuration and key/hash presence have SQL checks.
Reply targets and agent senders use foreign keys; missing references are refused.

## Transactions, notifications and migrations

`onChange` publishes only after a successful commit and never for idempotent
replays or rolled-back writes. It returns an unsubscribe function. Changes are
published in commit order even when a listener makes another mailbox call.
Listener exceptions become warnings; they cannot turn a committed operation
into an apparent failed command or prevent other listeners from receiving it.

Notifications are local to the mailbox instance. They are a scheduling hint,
not a durable event stream or cross-process bus. M3 will poll `PRAGMA data_version`
on its long-lived connection every 100 ms and query queues only when it changes;
local commits still wake the scheduler via `onChange`. See the
[M3 design decisions](m3-design.md) for the race handling and batch invariant. Queue state is
always authoritative in SQLite.

Public writes own their transaction. Calling them inside an existing transaction
is refused, preventing an inner operation from notifying before an outer commit.
Store write callbacks must be synchronous. M4 can introduce a transaction-aware
event dispatcher inside a new adapter when it needs to combine projections.

Opening the store checks the migration history under the writer lock. Schema
changes and their `schema_migrations` receipts commit together. Unknown or
gapped versions are refused. A failed migration rolls back its DDL and receipt.
`test/fixtures/store/v1.sql` is a frozen schema and queued-work fixture; preserve
it when adding later versions. A parity test compares its migrated schema with
a fresh database, verifies retained data, and checks foreign-key integrity.

## Verification

```sh
bun run check
bun run test:mailbox
bun run test:mailbox:repeat
```

The numbered cases in `test/mailbox.test.ts` cover acceptance cases 1–11 and 13;
case 12 is the frozen-v1 migration parity test in `test/store.test.ts`. Together
they verify all 13 “Done when” cases in the plan. The repeat command runs each
M2 test ten times, including actual competing Bun processes against one file.
The concurrency test holds the writer lock while both children start claiming,
then checks that every delivery was claimed exactly once.

Additional tests cover CLI persistence across process invocations, multi-agent
send, explicit database paths, lanes, literal flags, default reply handling,
invalid inputs, all final states, listener ordering, nested-transaction refusal,
project discovery/init, and cross-connection `data_version` semantics.
No model, credentials or provider process is needed for M2 verification.

The optional `deliver --once` bridge is left for M3. Scheduling, token budgets,
turn execution, event sourcing and boot recovery remain their planned milestones.

Verified locally on 2026-11-04 with Bun 1.4.4 / SQLite 3.51.0:

## Read-after comparison

After writing the implementation, reviewed the plan's pinned OpenBot references:
[mailbox store](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/mailbox-store.ts),
[schema](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/openbot-database-schema.ts),
[migration guidance](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/AGENTS.md)
and [schema parity tests](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/openbot-database-schema-parity.test.ts).
No implementation was copied.

That review highlighted queue edits, attachments and continuation metadata outside
M2's scope. It also reinforced immutable shipped migrations and rollback coverage.
Kru uses one migration path for both fresh and existing databases, avoiding a
separate latest-schema definition. The frozen v1 fixture independently guards
schema parity and retained data. Input size limits and secret redaction for stored
provider errors remain release-checklist work before v0.1.
