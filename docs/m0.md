# M0 — JSON-RPC over stdio

Status: implemented. Scope and acceptance criteria come from pages 10–14 of
[Kru — Project Plan & Milestones](Kru_Project_Plan_and_Milestones.pdf).

## Boundaries

The transport knows JSON-RPC messages and processes. It has no provider-specific
methods, sessions, persistence, retry policy, or engine concepts. Outbound
requests, inbound requests, responses, and notifications use the same newline
framing. Incoming envelopes may omit `jsonrpc` for Codex compatibility. If present,
the field must equal `"2.0"`. Batches are not supported. `jsonrpcField` defaults
to `true` and controls the field on every outgoing message; set it to `false`
for Codex and leave it enabled for peers that require JSON-RPC 2.0 envelopes.

The public exports are in `src/rpc/index.ts`. Options match the plan. Read-only
`pid`, `pendingRequestCount`, and `queuedWriteBytes` provide lifecycle and queue
observability without exposing mutable internal state.

## Failure behavior

- Stdout is split on newline bytes before strict UTF-8 decoding. The line limit
  excludes the newline and applies to both incoming and outgoing frames.
  Oversized incoming lines fail the connection; oversized outgoing frames reject
  their individual write. CRLF is accepted.
- Malformed JSON, invalid UTF-8, and invalid envelopes emit `bad-line` diagnostics.
  A valid message resets the consecutive bad-line counter. The threshold is fatal.
- The stdin budget includes queued and active frames. Writes resume after `drain`;
  excess writes reject with `WriteQueueFullError`. Cancelling or timing out a
  queued request removes its unsent frame. Bytes already sent cannot be recalled.
- Requests have a timeout and optional cancellation and result decoding.
  A bounded map remembers the latest 1,024 timed-out IDs. A later response emits
  one `late-response` diagnostic whose `delayMs` measures time since timeout.
- Inbound requests receive the handler's result, `-32603` for handler failures,
  or `-32601` without a handler. Undefined results become JSON `null`. Shutdown
  aborts handler signals and suppresses late handler replies from the old process.
- Exit waits up to `stderrDrainTimeoutMs` (default 500 ms) for stderr to finish. Pending requests reject with the
  same `ProcessExitError`, including the actual exit code/signal and final stderr
  line. Stderr retains at most the last 8,192 characters of an unterminated line.
- Stop is idempotent, blocks new work immediately, and waits for shutdown. On POSIX,
  children run in their own process group: send SIGTERM, allow `stopGraceMs`
  (default 3,000 ms), then SIGKILL
  remaining group members. This cleanup also runs after unexpected exits.
- Each spawned process owns its listeners, request maps, buffers, and handler
  controllers. Guards ignore old-process events. Request IDs increase across
  restarts. No work is retried automatically.

Tests explicitly use a 100-ms grace and a 50-ms stderr timeout. Process-tree
tests run on macOS and Linux; CI repeats the suite ten times on Linux. Windows
has a `taskkill /T /F` fallback, but its process-tree behavior has not been validated.

## Process ownership and signals

`start()` writes one mode-0600 JSON ownership record per spawned child
under `processRecordDir` (default `.kru/processes`, relative to the working
directory). Records contain the owner PID, child PID, POSIX process group ID,
platform, recording timestamp, and the child's OS start identity when available.
Linux uses boot ID plus process start ticks; macOS uses the UTC process start
time. No arguments or environment variables are stored. Directory creation fails
before spawning; if writing the record fails after spawning, the connection
shuts the child down. Each process has its own file, so concurrent owners do not
overwrite one another's records.

Publishing is atomic: write a same-directory `.tmp` file, fsync and close it,
then rename it to the final `.json` path. A process crash during the write can
leave an unpublished temporary file, but not a half-written final record.
`readProcessRecords()` returns schema-checked candidates, ignoring `.tmp` files,
malformed/truncated JSON, and invalid schemas without deleting them. It does not
kill processes. Tests leave both a truncated `.json` and abandoned `.tmp` files
beside a complete record and verify only the complete record is returned.

Completed tree cleanup removes the file. Failed tree cleanup preserves it.
SIGKILL cannot be caught and leaves ownership records behind. M7 must verify
that the owner is gone and the live child still matches its recorded identity
before terminating anything; a PID alone is insufficient because PIDs are reused.
Identity can be null if the OS does not support capture or the child already
exited. No orphan termination or boot recovery is performed at M0, and there is
an unavoidable window between OS spawn and recording its PID.

The CLI installs `installRpcSignalHandlers` for its active connections and returns
130/143 after SIGINT/SIGTERM cleanup. The first signal stops every registered
connection gracefully. A second signal calls `forceStop()` on every tracked
connection, signalling all process groups with SIGKILL immediately. It interrupts
the grace periods and stderr waits, reaps the children, and exits the host with
the first signal's exit code even if other application work keeps it alive.
Library consumers explicitly opt in; individual transports never install global
signal handlers. The lifecycle tests verify graceful cleanup, forced shutdown of
two resistant groups with grandchildren, and durable records after SIGKILL.

## Acceptance coverage

All 14 numbered cases live in `test/rpc.test.ts`. After every transport test,
cleanup verifies no pending requests, queued bytes, running tracked processes,
or unhandled promise rejections remain.

| Case | What it proves |
| --- | --- |
| 1 | Ping/pong round trip |
| 2 | 100 concurrent responses reach their callers in shuffled order |
| 3 | Remote error code, message, and data survive |
| 4 | Stalled requests time out |
| 5 | Notification order is preserved |
| 6 | Reverse requests receive handler results |
| 7 | Split UTF-8 and merged frames are decoded correctly |
| 8 | A bad line between valid messages does not discard them |
| 9 | Crashes reject every pending request, with final stderr and one exit event |
| 10 | Stop kills a resistant descendant and rejects subsequent calls |
| 11 | Stderr is diagnostic output, separate from protocol data |
| 12 | 50 MiB of attempted writes obey the configured queue bound |
| 13 | A response after timeout emits one late-response diagnostic |
| 14 | Requests without a handler receive `-32601` |

Additional cases cover omitted/wrong version fields in both wire modes, graceful
shutdown beyond 100 ms, process ownership, signal handling, backpressure recovery,
crashes with blocked stdin, queued
cancellation, handler failures, line limits, bad-line thresholds, invalid UTF-8,
decoders, aborts, missing executables, restarts, stale handler completions,
framing boundaries, and CLI success/error behavior. Tests require no network or
credentials and normally finish in about two seconds.

Verified with Bun 1.4.4 on macOS:

- Strict TypeScript checking passed.
- The initial M0 release passed all 32 tests in approximately 1.2 seconds.
- The initial ten repeated runs passed all 320 cases, including the per-test hygiene checks.
- The frozen lockfile install and both ping/stall CLI commands passed.

The compatibility and lifecycle follow-up passes all 46 tests, including 460
cases across ten repeated macOS runs. Linux CI runs the same ten-repeat command.

For v0.0.2, the regular suite passes 51 tests with one opt-in smoke test skipped;
ten repeated macOS runs pass all 510 regular cases. The separate real-Codex suite
passes both its connection-factory check and exact-byte initialize smoke test.
Type checking and the frozen-lockfile install also pass.

## Real-Codex smoke test

`bun run test:codex` runs an opt-in initialize-only exchange against an installed
Codex CLI. It uses `createCodexRpcConnection` from
`src/providers/codex/transport.ts`, which explicitly sets `jsonrpcField: false`.
The future M1 adapter must use this factory. This is connection setup only;
the ProviderClient adapter is still M1 work.

A transparent subprocess records the bytes before forwarding them to the real
`codex app-server --listen stdio://`. The test compares the entire byte stream
to literal headerless `initialize` and `initialized` frames. A repeated initialize
request receives `Already initialized`, providing a forwarding barrier before
checking the capture. This follows the
[official initialize exchange](https://learn.chatgpt.com/docs/app-server#initialization).
No thread, turn, model call, or credentials are needed. CI installs Codex 0.165.0
in a separate job to run this smoke test; the default suite skips it unless
`KRU_TEST_CODEX=1` is set. `KRU_CODEX_COMMAND` can select an alternate executable.
