# M4 — Event log, conversation history and cost projections

Implemented from pages 43–48 of the updated
[Kru project plan](Kru%20%E2%80%94%20Project%20Plan%20%26%20Milestones.pdf).
This completes the event/history work following the durable budget foundation
shipped in v0.0.5. The database upgrade is **v4**: v3 already shipped for usage
accounting, so the plan's proposed v3 migration is implemented as the next version.
Shipped migrations v1–v3 are unchanged.

## Try it

```sh
bun run dev -- init
bun run dev -- agent create reviewer --provider fake
bun run dev -- send reviewer "remember this message"
bun run dev -- daemon
```

In another terminal:

```sh
bun run dev -- log reviewer --follow
bun run dev -- cost --by agent --since 7d
bun run dev -- replay --verify
```

Stop the daemon and start it again; `log reviewer` retains both the input and the
assistant's answer. Use `--json` on all three read commands (`log` emits one JSON
object per line). `log` accepts
`--main` or `--lane <id>`; without a lane filter it includes every lane. `cost`
accepts `--agent`, `--by agent|model|chain` and `--since 7d` or an ISO timestamp
with a timezone. All commands retain project discovery, `KRU_DB` and `--db`.
M1's direct `chat` remains a separate transient conversation; M4 records daemon turns.

## Write path and transaction ownership

`src/store/events.ts` owns `dispatch`, typed event append, payload-version reads
and durable command receipts. `Store.command` and `Store.atomic` route through
it. The outer dispatcher acquires SQLite's writer lock before looking up the
receipt, so competing processes cannot both execute one command id. A matching
repeat returns the JSON result without running its handler or appending events;
reusing the id with different command input is refused.

Nested commands use savepoints and share the outer command id on their events.
Only the outer dispatcher commits. An inner failure rolls back its events,
receipt, projections and pending Store notifications, even when a caller catches
the error. Projectors never open transactions or read clocks, generate ids or
perform network work. They receive all ids, ordering and timestamps from payloads.
Store notifications publish after commit, preserving the existing scheduler wake-up bus.

`src/store/projectors/index.ts` projects seven tables: `agents`, `messages`,
`deliveries`, `turns`, `thread_messages`, `prices` and `usage_records`.
Mailbox and registry APIs remain compatible; their domain writes now emit events.
An enqueue contains its message and fanout; delivery transitions retain exact
sequence numbers, retry lineage, batch ids and timestamps.

Operational state remains outside replay: `active_lanes`, `daemon_lock`,
`agent_sessions` and `turn_scratch`. Lane reservation/release still participates
in its owning command's transaction. Boot preserves session bindings for M3's
resume-first behavior. Replaying history does not recreate locks or native processes.

## Event contract

The event envelope stores sequence, UUID, command id, type, payload version,
JSON payload and UTC occurrence time. Database triggers forbid updates/deletes
to events and command receipts. New payloads use version 1; the version-0
`agent.configured` compatibility fixture demonstrates the upcaster from the old
`agent` envelope to the current `row` envelope. Unknown versions/types fail
verification instead of being skipped. Version 0 is a compatibility test shape,
not a claim that an earlier released Kru version already stored domain events.

| Events | Projection |
| --- | --- |
| `agent.configured` | Agent configuration |
| `message.enqueued`, `message.imported` | Input messages and enqueue fanout |
| `delivery.imported`, `claimed`, `running`, `restored`, `finished`, `cancelled`, `retried` | Delivery state |
| `turn.prepared`, `turn.started`, `turn.completed` | Provider identity, model/profile/prefix, status/error/duration |
| `item.completed` | Assistant text, tools, commands and file changes |
| `price.configured` | Immutable model/rate snapshot |
| `usage.prepared`, `usage.checkpointed`, `usage.recorded`, `usage.imported`, `usage.resolved`, `usage.abandoned` | Latest usage and resolution state |

Checkpoint events replace the turn's latest snapshot. `usage.recorded` stores
the final value, not the sum of cumulative usage notifications. Reconciliation
has a separate event and retains the original estimate.

## Recording a turn

`src/turns/recorder.ts` implements the history port injected into the scheduler.
It records agent/lane, batch and causing deliveries/chains, native thread/turn,
model, profile and prefix hash. The runner passes only notifications belonging
to its confirmed native turn. Final provider items retain text and details,
including Codex command/file fields and Claude tool input/results.

Deltas go to in-memory Store listeners on `turn-delta`; there is no delta event
type. The recorder tolerates text arriving before `item/started`. While dirty,
it writes a scratch snapshot at most every two seconds. Another process's
`log --follow` checks `data_version` every 100 ms and reads those partial snapshots
and committed history. It emits updates rather than claiming token-by-token
cross-process streaming. Finalizing unchanged text does not print the answer twice.

A turn end performs one dispatch: remaining item events, turn completion, every
delivery's final transition, final usage and lane removal. Failure in any projector
rolls everything back, including receipts and notifications. A spent budget can
never observe a completed delivery whose final accounting transaction failed.

On boot, unfinished turns become interrupted; available scratch text is retained
as an explicitly partial item. Scratch is deleted only inside the recovery or
completion transaction. With a crash before the next snapshot, up to two seconds
of partial text may be lost. Full provider reconciliation remains M7; uncertain
turns are never automatically retried.

## Prices, costs and budget days

`src/cost/prices.ts` provides the persistent `PriceBook`. Rates have provider,
model, effective timestamp, source and a stable content-derived id. Adding a new
effective price does not modify existing snapshots. Every priced turn stores its
price id and original rates. The first observed estimate pins its price for later
checkpoints; new turns select the applicable effective price. Unknown models
have NULL `price_id` and `cost_usd`, and appear as unpriced in `cost`.

The scalar usage columns preserve input/cache/output counts and cache-write
lifetimes. `cost_usd` is the estimated upper bound when lifetimes are incomplete;
the full lower/upper bounds remain in `cost_json`. Integer nano-USD calculations
and both token/USD budget gates are retained. The scope is still the explicit
main-agent token estimate described in [usage and pricing](usage-and-pricing.md),
not an invoice or an assertion that auxiliary model/tool charges are included.
No new price verification or live model benchmark was needed for M4.

`recorded_at` is an immutable UTC accounting timestamp initialized from the turn
start, preserving v0.0.5's day attribution. Budget queries translate the configured
local-day boundaries into UTC ranges. Changing the timezone changes the selected
calendar window; it never rewrites timestamps, historical rates or counters.
Different windows can naturally include different completed turns. Unresolved
consumption remains a conservative hold across midnight and restarts until an
explicit reviewed bound resolves it. This distinction avoids treating a timezone
change as a data migration or claiming that two different local calendars have
identical boundaries.

Cost grouping counts each turn once. If a user batch contains multiple chains,
`--by chain` uses a shared chain-set bucket rather than duplicating the whole turn
cost for each chain. `--since` filters UTC accounting timestamps. Incomplete and
unpriced records are visible alongside partial known totals.

## Migration and verification

The v4 migration and genesis import share one transaction and migration marker.
Existing agents, input messages, deliveries and usage become events; deliveries
are imported in original seq order, and message insertion order preserves reply
references. Existing cost JSON stays unchanged and receives a matching price id.
No pre-M4 assistant answer is invented when older schemas did not store one.
Reopening an upgraded database does not import genesis a second time.

`replay --verify` pins events and source projections to one read snapshot, replays
into a separate in-memory database and compares every projection row and column.
It reports differences and exits 1 on drift. It never repairs or clears the live
database. The library's `replay` returns an isolated rebuilt database; operational
tables remain empty. Command receipts are durable execution records, not rebuilt
domain projections.

The twelve numbered cases in `test/events.test.ts` follow the PDF's acceptance
table: busy replay, deterministic replay, command deduplication, atomic turn-end
failure, restart history, cost/event agreement, unknown prices, price changes,
restart budgets, timezone-safe timestamps, old payloads and frozen-v2 import.
Additional cases cover live scratch reads, native item details, immutable logs,
competing command processes, v4 rollback/retry and repeated SIGKILL with old
unresolved usage. Frozen v1/v2/v3/v4 fixtures retain migration parity coverage.

## Read-after comparison

After implementing Kru's version, reviewed pinned OpenBot
[dispatch](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/database/database-core.ts),
[replay](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/database/thread-replay.ts)
and [transaction rules](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/AGENTS.md).
Their ownership model reinforced keeping nested projection work inside the outer
transaction. Kru additionally checks command-input conflicts and serializes the
receipt lookup under the writer lock.

The [delta buffer](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/agent/delta-buffer.ts)
and [turn lifecycle](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/agent/turn-lifecycle.ts)
reinforced retaining pending text at completion; Kru deliberately keeps individual
deltas out of its log and uses the plan's separate scratch snapshots. Reviewing
[usage collection](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/agent/usage-collection.ts),
[usage pricing](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/agent/usage-pricing.ts)
and [agent usage](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/database/agent-usage.ts)
also reinforced snapshot replacement and explicit accounting scope. Broader native
query-pipeline billing remains a separate follow-up rather than an unsupported
claim about these token estimates.
