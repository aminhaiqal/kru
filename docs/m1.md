# M1 — One protocol, three adapters

M1 now includes fake, Codex and Claude adapters behind the same typed provider
port. Claude translates SDK events, invented turn IDs, end-of-turn usage, an
in-process MCP server and a persistent streaming input queue into that port.
The chat consumer imports only the port; the registry selects the adapter.
There is still no mailbox, SQLite engine store or scheduler (M2–M3).

## Run it

```sh
bun install
bun run dev -- chat --provider fake "hello"
bun run dev -- chat --provider codex "hello"
bun run dev -- chat --provider claude "hello"
bun run dev -- chat --provider claude
```

With no prompt in a terminal, chat keeps a thread open until `/quit`, `/exit`,
or EOF. Non-terminal stdin becomes one prompt. Real adapters use the operator's
existing provider login/model configuration. Tests that make model calls are
opt-in and consume that account's quota.

Each turn prints its reply on stdout and normalized usage on stderr:
`inputTotal`, `cachedRead`, `cacheWrite`, `output`, and `total`.
If the provider exits before reporting usage, the CLI prints `usage: unavailable`.
Claude's SDK `usage` is per turn; `modelUsage` is a cumulative session snapshot.
The adapter keeps those distinct, including when a native session is resumed.

Both `TokenUsage.last` and `.total` use the same units: `inputTotal` includes
uncached input, cache reads and cache writes; `cachedRead` and `cacheWrite` are
disjoint subsets of that total. `totalTokens` is `inputTotal + output`. Uncached
input is `inputTotal - cachedRead - cacheWrite`. Fake usage uses deterministic
character counts for tests, with zero cached tokens, rather than a model tokenizer.

Claude adds `input_tokens`, `cache_read_input_tokens` and
`cache_creation_input_tokens` to form `inputTotal`. Codex's `inputTokens` already
includes its `cachedInputTokens` and `cacheWriteInputTokens`, so the adapter copies
the total without adding them again. Older Codex versions that omit the write
counter report zero writes. Invalid negative, fractional or inconsistent counts
are rejected. Conformance checks both per-turn and cumulative cache invariants,
with nonzero cache fixtures and an equivalent-usage cross-provider regression.

These are token counts, not currency or a savings estimate. The later ledger must
price reads and writes separately using model and cache-lifetime rates. The
normalization follows the
[Anthropic token breakdown](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
and [OpenAI inclusive cache accounting](https://developers.openai.com/api/docs/guides/decisions#reuse-shared-input-with-prompt-caching).

## Agent configuration and prompt profiles

`ThreadParams` contains `cwd`, `model`, `instructions`, `tools`, `promptProfile`
and `permissions`. Permissions include `sandbox`, `approvalPolicy` and optional
`writableRoots` (relative paths resolve against `cwd`). They default to `read-only`
and `on-request`; neither
is hard-coded into the Codex adapter. `workspace-write` and `never` are explicit
configuration choices. Corresponding CLI flags are `--sandbox`,
`--approval-policy`, `--prompt-profile`, and repeatable `--writable-root <path>`.

```ts
const provider = createProvider('claude');
await provider.start();
const { thread } = await provider.request('thread/start', {
  cwd: process.cwd(),
  promptProfile: 'coding',
  permissions: { sandbox: 'workspace-write', approvalPolicy: 'on-request' },
});
```

`minimal` uses a short custom instruction prefix. `coding` uses a short coding
prefix. Claude's `full` profile uses `systemPrompt: { type: 'preset', preset:
'claude_code' }`, appending only explicit agent instructions. It uses the standard
Claude Code tool preset and `settingSources: ['project', 'local']`, loading project
CLAUDE.md, rules and settings. It also retains the native turn-start attachment
pass; the lean profiles use `client_composed` messages. User settings are excluded
to make the project baseline reproducible. Codex rejects this Claude-only profile.

Agent instructions follow the stable profile text; timestamps, IDs,
usage and per-turn messages never enter it. Tool declarations are canonically
ordered and snapshotted so caller mutation and object insertion order cannot
change a running thread's prefix. Resume uses the original configuration unless
explicit changes are supplied, without prepending the base instructions twice.

`prepareThread()` rejects an instruction string of 8,000 bytes or more, and a
seventh declared tool, both at start and resume. `Thread.prompt` reports the
profile, instruction byte count, Kru-declared `toolCount` and SHA-256 prefix hash.
Claude also reports `builtinToolCount` separately; its selected built-in tool list
participates in the prefix hash. Providers whose native tool set is not controlled
by Kru omit that count.
For `full`, the count comes from native SDK initialization and is available on
subsequent `thread/resume` results. Its prefix hash identifies Kru's preset
selection and appended instructions, not the provider's evolving prompt or
project files. Its instruction byte count measures only the appended Kru text;
actual full-context size is measured by normalized usage.
These measure **Kru-controlled instructions and tool declarations**, not a cap on
provider-owned harness text, native Codex tools, project files, conversation
history or total model context. Provider-reported usage measures actual tokens.

The lean Claude profiles receive a custom `systemPrompt`, `settingSources: []`, and an explicit
built-in tool list rather than the full Claude Code preset. Its minimal profile
has no built-ins. The coding profile selects `Read`, `Glob` and `Grep` for read-only
agents, and `Read`, `Edit`, `Bash`, `Write`, `Glob` and `Grep` for writable agents.
Built-ins do not consume the six-tool Kru declaration budget: a writable coding
agent can retain all six built-ins alongside six Kru tools, including
`send_message` and `list_agents`. Declared SDK MCP tools still route through the
engine's tool callback.

On native approval requests, the port emits `approval/request`. A host answers
with `respond(id, { decision: 'accept' | 'decline', content? })`. Codex command,
file, permission and MCP elicitation responses are translated to their native
shapes. Claude uses `canUseTool` to enforce read-only restrictions and request
host decisions for shell commands and file writes outside the configured roots.
With `workspace-write`, `Write`, `Edit` and `NotebookEdit` inside `cwd` or a
`writableRoots` entry are allowed without an approval handler, including with
`approvalPolicy: 'never'`. Read operations remain allowed, as in Codex's read-only
filesystem policy. Read-only agents refuse file writes and sandbox escalations.
Claude's pre-tool hook enforces these decisions before native project allow rules
and `dontAsk` can skip `canUseTool`; missing/unresolvable paths fail closed or ask.
New paths are checked through their existing physical ancestor; symlink escapes,
traversal and sibling-prefix paths cannot gain an automatic grant. Protected
`.git`, `.codex` and `.agents` metadata also needs explicit approval.

Codex receives the same extra roots in its native sandbox configuration. Its
implicit `/tmp` and `$TMPDIR` write grants are disabled so unlisted temporary
directories do not bypass the shared root contract; explicitly add a temporary
root when an agent needs it. Claude uses file-tool policy hooks rather than an OS
sandbox; arbitrary shell access still requires a host decision. A host accepting
a shell command is responsible for its effects. Codex can run commands in its
native sandbox without asking; its escape requests use the same host decision
bridge. Native deny rules may still reject operations a host approves.

Missing approval handlers decline rather than hanging or auto-granting access.
The CLI shows command/file request details and asks `Allow this action? [y/N]`
when stdin and stderr are terminals and the policy is `on-request`, including for
a prompt passed as an argument. Only `y`/`yes` approves, once. Other answers, EOF,
non-terminal runs and `never` decline. Approval answers and chat messages share
one input reader; pretyped lines are discarded while the assistant works. Requests
are prompted sequentially. Cancellation or the existing provider deadline closes
input, preventing a late answer from authorizing another request. The default
provider request deadline is 30 seconds.

Structured permissions/elicitation/tool-input requests remain declined by the CLI;
embedding hosts supply their own decision logic. Codex may execute in-sandbox
commands without requesting approval, so this UI does not close the native shell
parity gap. The `never` option can deny
native MCP/elicitation operations, so it is not the default.

Resume accepts the original tool definitions because Claude must rebuild its
in-process MCP server after reconnecting. Known Claude sessions reuse their live
input queue. A replacement adapter can discover a stored native UUID with the
SDK's session metadata API and open it on the next turn. Codex restores its
native dynamic tools from its session cache. Provider session files remain cache;
Kru's durable engine history is later work.

## Shared Codex runtime and fault isolation

Default Codex agent views share one `CodexRuntime`/app-server process. A custom
runtime can be supplied explicitly; transport overrides create an isolated runtime
for tests or dedicated deployments. Initialization runs once. Thread ownership
routes notifications, tool calls, approvals and activity to the correct view.
Thread registration is serialized to attribute startup requests; turns on distinct
threads run concurrently. Stopping a view interrupts its work and releases its
ownership without stopping other agents. The last view stops the process.
`forceStop()` is an administrative operation on the shared process.

One malformed known notification emits a diagnostic, fails the affected turn,
suppresses its stale deltas and requests interruption. It does not kill other
agents. Three consecutive malformed known notifications terminate the process;
a subsequent explicit start can replace it. Unknown native notification methods
are tolerated. No failed or unknown turn is automatically replayed.

Both real adapters reject overlapping `turn/start` calls for a thread. Codex's
native implicit steering is not enabled through a port that advertises steering
as unsupported. A timed-out start retains its unknown-outcome reservation until
completion or exit. Thread/turn boundaries, item events, deltas, token usage,
tool requests and permission requests have compiler-checked types.

## Chat liveness and cancellation

`--idle-timeout-ms` defaults to 120,000 ms. `--timeout-ms` remains an alias for
that idle limit, not a wall-clock turn limit. `runChatTurn({ idleTimeoutMs })`
resets the timer on correctly scoped notifications/activity, including native
reasoning and SDK tool-progress messages. Another agent/thread cannot keep an
idle turn alive. A coding turn can run longer than two minutes while progressing.

Native `item/commandExecution/outputDelta` and progress notifications reset the
Codex watchdog through scoped activity; Claude SDK `tool_progress` messages do
the same. An explicitly running command suspends the model-idle watchdog even
when it has no output: Claude's Bash tool-use/result pair maps to common
`commandExecution` item boundaries. The idle clock starts again when the last
command completes. This is not a command deadline; native command timeouts and
user cancellation still apply, including if a command hangs. The regression
fixtures cover several idle windows with no events, periodic output/progress,
resumption of idle detection after completion, and cancellation while quiet.

Messages are created on their first delta even if `item/started` arrives later.
Early events are bounded and buffered until the turn ID is known. Completed
items with final text work without deltas, and final text is not printed twice.
All per-turn listeners are removed on completion, failure, cancellation and exit.

Tool and approval replies are tracked exactly once. Missing tool listeners get
`-32601`; unanswered calls have a bounded deadline. Rejected async handlers become
internal errors without unhandled rejections. Stop, interruption and deadlines
abort handlers. IDs are not reused across process restarts, so stale replies
cannot answer new calls. The existing first-signal graceful stop and second-signal
force-quit behavior applies to all providers. Claude subprocesses also use
process groups and atomic ownership records.

## Tests and canary

```sh
bun run check
bun run test:providers
bun test test/cli-approvals.test.ts # offline approval routing and terminal regressions
bun test --rerun-each 10
bun run test:codex        # real initialize + experimental registration, no model
bun run test:codex-chat   # real Codex model turns; uses existing login/quota
bun run test:claude-chat  # real Claude queue/MCP/usage/resume; existing login/quota
bun run benchmark:claude-profiles # real full vs coding task; existing login/quota
KRU_TEST_PERMISSIONS=1 bun test test/permissions-live.test.ts # real CLI writes and denied escapes
```

The same conformance cases run against all three adapters. Codex uses a scripted
native stdio peer in offline tests. Claude uses SDK events and a real in-memory
MCP client/server transport, not a fake JSON-RPC adapter. Explicit cases **#7** and
**#8** check prefix stability across turns/resume and the instruction/tool budget.
Additional tests cover shared-process ownership, isolated malformed events,
repeated-fault escalation, permission/elicitation mapping, idle progress, CLI usage,
errors, crashes, interrupted tools, stale replies and asynchronous handler failures.
Permission conformance runs the same action table through fake, a scripted Codex
sandbox peer, and Claude's real hook/callback options. Separate opt-in real-CLI
checks create files in the workspace and an extra root, and verify an outside
write is refused with `never`. The Codex smoke test independently checks the
native sandbox's returned writable roots without a model call.

Real terminal checks on November 4 verified Claude's `coding` profile with
`workspace-write` / `on-request`: `yes` created the requested marker and exited
0; `no` left it absent and exited 0; Ctrl+C during the prompt left it absent and
exited 130. [Captured transcripts and marker results](verification/cli-approvals-2026-11-04.json)
record these three runs. Offline regressions also cover EOF, request deadlines,
sequential prompts, pretyped consent and control characters. Requests without a
command or file path to review are declined without prompting.

The same real-terminal checks passed with Codex CLI `0.165.0`: approval created
the marker (exit 0), refusal left it absent (exit 0), and Ctrl+C left it absent
(exit 130). [Codex transcripts and marker results](verification/codex-cli-approvals-2026-11-04.json)
record an explicit `require_escalated` request. Normal sandboxed commands do not
necessarily request approval; these checks verify the host bridge, not strict
shell parity. An offline native-peer test checks that `yes`, `no` and Enter reach
Codex as exactly `accept`/`decline`, without a persistent execution-policy grant.

The profile benchmark uses two fresh workspaces, one fixed model, identical
instructions and a duration-parser implementation task. The host grants the same
tool permissions in both runs, then independently runs the unchanged 26 acceptance
tests. It records native model/version/tool initialization, per-turn and cumulative
usage, generated code, output and test logs under `.kru/benchmarks/`. Auto memory
is disabled for both runs; project instructions are available to both. The runner
uses `full` then `coding`, so it is a paired observation rather than a controlled
multi-run savings estimate. No costs are inferred from raw token totals.
The [first completed comparison](benchmarks/claude-profiles-2026-11-03/README.md)
records both implementations passing 26 tests, lower input/total tokens for
`coding`, longer elapsed time and higher cache writes.

Pinned CI remains on Codex 0.165.0. `codex-canary.yml` separately installs `latest`
every night at 03:17 UTC, records the version, and checks exact initialize bytes
and experimental dynamic-tool registration. It also generates the experimental
protocol schemas and checks tool-call method, parameter and result compatibility.
It makes no model call and needs no API credential. Invocation/output behavior is
additionally exercised by scripted tests; live model/tool calls remain opt-in.
The canary is on the repository's default branch (`main`) and active. A manual
verification on 2026-11-04 passed with latest Codex 0.166.0:
[GitHub Actions run 41780689738](https://github.com/aminhaiqal/kru/actions/runs/41780689738).
Cron remains 03:17 UTC daily; a schedule-triggered run was not observed in that
audit. See the [follow-up verification](follow-ups-verification-2026-11-04.md),
including the remaining distinction between shared file-policy conformance and
native shell approval behavior.

Local acceptance passed strict TypeScript checking, a frozen dependency install,
and ten repeated runs of the complete offline suite (1,020 passes, no failures).
Real Codex and Claude model tests also passed, including streaming, usage,
resume, tool calls and interruption through the common port.
