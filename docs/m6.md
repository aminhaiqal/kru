# M6 — Threads apart from provider sessions

Implemented against the expanded M6 specification, printed pages 59–66 of the
[Kru project plan](Kru_Project_Plan_and_Milestones.pdf), expanded 4 November 2026.
This follow-up replaces the earlier v0.1.1 implementation contract. The package
version remains v0.1.1 pending a release instruction. The
[original conformance audit](m6-conformance-review.md) is retained as historical
evidence; its findings are resolved by this implementation and acceptance suite.

## Try it

```sh
bun run demo:handoff
bun run test:threads:repeat
```

The demo runs ten turns through the Claude adapter, changes the agent to Codex
using the actual CLI, then answers a question about the first turn. The required
fact is deliberately outside the handoff packet: Codex retrieves its original
source with `history_search`. It asserts one logical thread, eleven native turn
starts, eleven delivery-backed ledger entries, confirmed handoff use and replay
parity. Claude uses scripted SDK messages with its real local MCP server; Codex
uses the real adapter over a scripted stdio peer. There are no model calls or
claims about live model recall quality.

## Identity and session preparation

Each `(agent, lane)` owns one permanent Kru thread. Original message IDs and
recorded executions link to that thread through events. Native session IDs stay
in operational provider bindings; they never substitute for public thread IDs.
Domain `session_generations` retain a monotonically increasing number, previous
generation, provider, configuration hash, runtime/account scope hash, replacement
reason and active/retired/quarantined state. A database index permits one active
generation per thread. M3's lane lease still permits one active execution batch.

The runner captures configuration and claims its batch before preparation. A
compatible session is resumed after restart; a live compatible session is reused.
Only a provider-classified missing cache causes missing-session replacement.
Authentication, rate-limit and transport errors hold the work visibly. Account or
runtime scope changes require a new generation. Adapters hash credential/settings
scope; Codex also reads native account identity locally without refreshing tokens.
Only hashes are retained for scope comparison. Switching A→B→A creates a fresh A
branch, preserving intervening B history. Edits during setup or execution take
effect at the next claim.

Preparation records a durable setup intent before native creation. The intent
captures owner epoch, claimed batch, expected generation, configuration, source
cutoff and frozen packet. Native creation happens outside the transaction; its
returned candidate ID is retained before activation. One writer transaction
checks the owner, lane lease and expected generation, then retires the old
generation, activates the new generation, stores the packet and binds the native
cache. A competing or stale candidate cannot activate.

A timeout remains `setup_unknown`; it is not treated as missing and no task turn
has been submitted. Failed activation cleans the unused candidate or holds it in
`cleanup_pending`. Claude closes only its session; Codex unsubscribes and archives
only its candidate, tolerating an absent rollout for an unused thread. Unknown
native starts follow M3/M7's no-automatic-resend policy and quarantine the exact
generation. Old execution notifications/tools cannot mutate the replacement;
valid committed M5 receipts remain replayable without another enqueue.

Only the runner sends `turn/start` for a claimed delivery. Session preparation,
handoff rendering, search and cleanup never start a hidden model turn.

## Canonical history and handoff

Incoming source messages appear once, including sender, reply, chain/hop and
execution provenance. Retries add execution-attempt markers rather than copies
of the request. Each batched message remains individually associated with its
execution. History includes assistant text, recorded tool/command/file results,
execution outcomes and explicit partial/interrupted markers. Delivery and item
sequence determine ordering even when the clock moves backwards. Starting,
queued, cancelled and rejected-before-execution input is excluded from recall.
Native hidden reasoning is excluded. Retrieval tool calls/results remain in M4's
audit log, but their derived bodies are excluded from canonical search evidence.

The deterministic extractive packet defaults to **12,000 Unicode code points**,
including its wrapper. `daemon --handoff-chars <count>` accepts 512–16000.
The runner reserves current input first, then fits history into the remaining
32 KiB turn limit and any smaller advertised provider input limit. Oversized
current input fails before native setup/submission. The current request appears
once, after the history boundary, and stays outside the stable system/tool prefix.

The builder considers the first two anchors and at most forty recent records,
including execution outcomes. It prefers whole entries, then labelled excerpts;
a tiny budget retains a compact history notice and source retrieval IDs. It
labels historical instructions as evidence, not new work. Unavailable migrated
history and clipping are explicit. No model-generated summary is used.

Each packet is stored with a renderer version, source event cutoff, switch reason,
included/clipped/omitted source IDs, current-message exclusions, character/byte
budgets, complete text and SHA256. A pending packet is read back unchanged rather
than rebuilt from newer history. A confirmed `turn/started` records the execution's
generation and `handoff.used` atomically with its running state. Setup-only crashes
retain the unused packet. After confirmed use, resume does not inject it again.

## history_search

The third Kru tool has this contract:

```ts
{ query?: string; messageId?: string; limit?: number; cursor?: string }
```

Exactly one of `query` or `messageId` is required. Search is literal and
case-insensitive with Unicode lowercasing. Exact lookup accepts an original
message ID, returned source ID or native item ID and reads the complete stored
body through continuation. The default limit is six, maximum twenty. Excerpts
are at most 800 Unicode code points. The serialized response is bounded by 8,000
code points and the provider's tool-result byte ceiling, including the result
envelope. An excessively small ceiling returns an error rather than an empty
success that would conceal matches.

```json
{ "query": "launch code", "limit": 6 }
```

Results contain `threadId`, `snapshotSeq`, `matches`, `nextCursor`, `omitted` and
known `gaps`. Matches expose `sourceId`, `executionId`, role, event sequence, text,
truncation, outcome and available provenance. For full text, use
`{ "messageId": "<sourceId>" }`, then repeat that selector with `nextCursor`.

Scope comes only from the trusted owning execution's agent and lane. Foreign
source IDs return no match. Opaque HMAC-protected cursors fix the thread, selector,
committed event snapshot and source/offset; edited or foreign cursors fail.
Immutable history versions ensure that newly committed turns or late items do
not enter subsequent pages of an earlier snapshot. Database lookup failures are
unsuccessful tool results and do not themselves stop the daemon.

`kru/threads` exports the storage, renderer and contracts. Legacy direct-library
`search`/`read` aliases remain for compatibility; the model tool uses the contract
above. Custom hosts must supply the lifecycle/history ports to obtain the default
daemon's durability guarantees.

## Migration and replay

Migration **v9** follows the existing v8 recovery schema without changing shipped
migrations or event payloads. It adds eight replay projections: `history_state`,
`message_threads`, `history_versions`, `history_gaps`, `session_generations`,
`handoffs`, `handoff_uses` and `turn_generations`. Replay now verifies **22** domain
tables. Setup attempts, native bindings and cursor-signing identity are operational
state; replay never creates or resumes an external provider session.

Genesis events import recorded source history and retained lineage. Legacy native
bindings are unverified: a unique newest candidate must agree with recorded
execution/provider, and its unknown runtime scope still requires fresh setup.
Ties/ambiguous candidates are retired rather than selected by provider name.
Unavailable pre-M4 output and incomplete earlier session lineage are reported as
gaps. Frozen v7/v8 fixtures verify rollback/retry, original event-prefix preservation,
foreign keys and deterministic replay twice into empty stores.
