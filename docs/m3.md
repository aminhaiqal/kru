# M3 — Lanes and the drain scheduler

Implemented from pages 31–38 of the updated
[Kru project plan](Kru%20%E2%80%94%20Project%20Plan%20%26%20Milestones.pdf),
with the recorded [design decisions](m3-design.md). M3 connects the M2 mailbox
to M1 providers. Every turn consumes an atomically claimed batch of deliveries.

## Try it without a model

Initialize a project and create an agent:

```sh
bun run dev -- init
bun run dev -- agent create reviewer --provider fake
bun run dev -- agent pause reviewer
bun run dev -- send reviewer "review the latest commit"
bun run dev -- daemon
```

In another terminal in that project or one of its subfolders:

```sh
bun run dev -- status
# "reviewer" "main" held paused
bun run dev -- agent resume reviewer
bun run dev -- status --json
```

The fake completes queued work without credentials. Completed deliveries leave
the active queue. Stop the daemon with Ctrl+C. `chat` remains a separate direct
M1 command. Durable assistant messages and `kru log` are implemented in [M4](m4.md).

For real work, create an agent with `--provider codex` or `--provider claude`.
Agent settings include `--cwd`, `--model`, `--prompt-profile`, `--instructions`,
`--sandbox` and `--approval-policy`. Configure write access deliberately, for example:

```sh
bun run dev -- agent create coder --provider claude --cwd .
bun run dev -- agent set coder --prompt-profile coding --sandbox workspace-write
bun run dev -- agent set coder --daily-tokens 200000
bun run dev -- agent pause coder
bun run dev -- agent resume coder
```

A daily limit of zero holds all new turns; an omitted limit is unlimited. Raising
a spent limit wakes its held lanes. Pausing affects future turns; it does not
cancel an active one. The daemon declines interactive approval requests and
rejects Kru tool calls until M5 supplies a tool router.

## Atomic batches and lanes

Migration v2 adds `active_lanes`, `agent_sessions`, `daemon_lock` and
`deliveries.batch_id`. The main lane is stored as the non-null empty lane key;
side-lane ids must be nonempty. The `(agent_id, lane_key)` primary key enforces
one active batch per lane. A unique batch id also guards ownership during release.

`claimBatch` reserves a lane and transitions its selected deliveries from queued
to starting in the same `BEGIN IMMEDIATE` transaction. It refuses lanes with
an existing reservation or legacy starting/running deliveries. `claimNext`
remains compatible with M2 callers but cannot bypass a batch reservation.

Only consecutive user deliveries at the lane head share a batch. The limits are
10 messages and 32,768 UTF-8 bytes, including the fixed separator
`\n\n--- Kru message ---\n\n`. An agent or routine delivery runs alone. Side lanes
are independent and can run concurrently.

An oversized single head is reserved alone and marked failed before any model
call, with a clear size error. This preserves its history and allows smaller
queued messages behind it to run. No submitted turn exceeds the byte limit.

`markBatchRunning`, `finishBatch` and `restoreBatch` transition every member
atomically. Completion and reservation deletion share a transaction. Restoration
retains original seq positions and clears the batch/turn ids. Stale completions
cannot release a later batch. Individual transition methods refuse active batch
members; callers must use the batch operations. A retry still creates a separate
queued attempt and never reopens a final delivery.

## Wakeups, holds and fairness

The daemon scans once at startup. Same-connection mailbox changes wake the
scheduler after commit; all mailbox adapters using that `Store` share a change
bus owned by the Store. The agent registry publishes committed configuration
changes on that same bus, and the scheduler subscribes to both ports. Other
connections are detected with `PRAGMA data_version` every 100 ms.
Samples are compared on the same long-lived connection, and the sample taken
before a queue scan becomes the baseline. An unchanged version does not cause
a queue scan. Local registry updates wake the scheduler automatically; no manual
`scheduler.refresh()` call is required. CLI changes use another connection and
wake through polling.

Scheduling uses separate scheduled and draining sets. A wakeup never starts a
turn directly. After a drain clears its flag and releases its slot, it reads the
queue again and reschedules eligible work. Slot release, provider readiness,
budget reset and configuration changes also wake held lanes.

Holds are evaluated in this order:

| Hold | Clears when |
| --- | --- |
| paused | `agent resume` updates configuration |
| provider-not-ready | Provider startup/session setup succeeds, or configuration is fixed |
| lane-busy | The reservation or legacy active work is released |
| budget | The local/configured calendar day resets or `dailyTokens` is raised |
| slots | A turn releases global capacity |

The default global cap is two. A reserved slot includes session setup and the
uncertain-start grace period. Eligible user-headed lanes go before other senders;
within each group, the lowest delivery seq wins. Budget counters use the latest
`last.totalTokens` snapshot per turn, applying its difference instead of summing
repeated usage events. Cache subsets are not counted again. Budgets are start
gates: already active turns may take an agent past its limit.

Daily windows reset at midnight in the configured budget timezone.
The subsequently added [usage ledger](usage-and-pricing.md) preserves counters
and estimated token costs across daemon restarts. The default timezone is the host's local timezone, resolved
once at startup. Use `kru daemon --budget-timezone Asia/Kuala_Lumpur` to choose an
IANA zone explicitly, or `--budget-timezone UTC` for UTC. Calendar-day comparisons
use `Intl.DateTimeFormat`, including daylight-saving changes. `status --json`
reports the active daemon's `budgetTimezone`.

[M4's first foundation](m4-plan.md) adds durable token and estimated-USD gates.
Unknown submitted consumption is preserved rather than reset to zero. The daemon writes its status snapshot only when it changes, enabling
another CLI process to display holds and token totals without redundant writes.
Active lane rows remain authoritative for running/starting status.

## Native sessions

Bindings are keyed by agent, lane and provider. Their `prompt_hash` is the M1
provider-reported prefix hash. An additional `config_hash` covers the stable
prefix, provider, model, cwd and permission settings. Pausing and budget changes
do not rotate a native session.

An unchanged live binding is reused. After a daemon restart, the runner attempts
`thread/resume`; a missing native cache starts a fresh session. A different
configuration or returned prefix starts a fresh session as well. Other setup
failures restore the batch at its original queue position and hold the provider
for recovery, without sending `turn/start`.

Provider session files remain disposable caches. M3 has no cross-provider
handoff or durable conversational history; those belong to M6 and M4. The startup
sweep preserves native bindings for interrupted batches. The next delivery tries
`thread/resume` first. A definitively missing/unusable cache is replaced after
resume fails; a transient service error holds work and preserves the binding.

## Turn outcomes and shutdown

| Event | Batch outcome |
| --- | --- |
| Confirmed completed / failed / interrupted | Matching final state |
| Setup failure before `turn/start` | Restored to queued, provider held |
| Definite `turn/start` RPC refusal | Failed |
| Unknown start result | Starting until confirmation or grace expiry |
| Five-minute unknown-start grace expiry | Interrupted |
| Provider exit or running-turn idle timeout | Interrupted |

The runner installs listeners before submitting the turn. A late `turn/started`
confirms the original batch; it never starts a replacement turn. Unconfirmed
start events have a bounded buffer. Output, progress and tool activity reset the
idle deadline; explicitly active native commands suspend it until completion.

When a turn remains uncertain, the scheduler calls the provider port's
`retireThread` before releasing the lane. Codex installs a tombstone on that
native thread and keeps the shared process alive. Late `turn/started` events
cause an immediate `turn/interrupt` for that thread/turn. Late receipts are also
cancelled when available. All output, usage and malformed notifications for the
retired thread are discarded; approval requests are declined and tool calls are
rejected. Tombstones stay until the shared process exits and prevent resuming a
retired thread. New work uses a fresh native thread without interrupting peers.

Native request timeouts and thread retirement also trigger one coalesced local
[`config/read` probe](https://learn.chatgpt.com/docs/app-server#config-rpc-examples-for-app-settings),
with `includeLayers: false` and a two-second deadline. A response, including an
RPC error, proves the process is answering. Only a probe timeout force-stops the
shared process for this failure. A generation check prevents an old probe from
killing a replacement process. Queued work restarts it through provider readiness.
Claude retains per-thread process termination. No uncertain turn is retried.

Daemon ownership uses the existing M0 process-start identity helper. A live
matching PID refuses a second daemon even if its heartbeat is old. A dead PID
or changed start identity allows takeover. Heartbeats run every ten seconds and
update only the heartbeat timestamp. Status writes occur only when the snapshot
changes. Updates/releases still match the owning PID and identity; heartbeat age
does not authorize takeover.

After acquiring the lock and before starting any provider, the daemon marks all
starting/running deliveries interrupted with `daemon restarted`, clears lane
reservations while preserving session bindings for a resume attempt. This is M3's minimal recovery;
M7 adds provider reconciliation and orphan-process recovery.

Shutdown stops claims, waits up to five seconds by default, then interrupts
remaining turns and stops providers. A second SIGINT/SIGTERM force-stops tracked
runtimes immediately. Provider setup waits are cancellable, so a stalled startup
cannot hold shutdown forever.

Daemon flags include `--max-turns`, `--poll-ms`, `--idle-timeout-ms`,
`--start-timeout-ms`, `--start-grace-ms`, `--shutdown-grace-ms` and
`--budget-timezone`.
All daemon/status commands use the same project discovery and explicit database
overrides as M2. The resolved database remains fixed for the daemon's lifetime.

The twelve numbered tests in `test/scheduler.test.ts` map directly to the plan's
acceptance cases. They include actual CLI sends from another process, competing
batch-claim processes, two-daemon refusal, a forced lost-wakeup gap, and a real
SIGKILL/restart. Tests use shortened grace periods instead of waiting five minutes.

Additional tests cover rollback and stale release, byte/count limits, provider
setup failure, late confirmation, idle expiry and native command liveness,
usage deduplication, midnight reset, session reuse/configuration changes,
shared-connection mailbox/registry wakeups, PID identity takeover, CLI holds,
double-signal shutdown, unchanged-status write suppression and timezone/DST
boundaries. Real stdio Codex fixtures verify that uncertain thread retirement
preserves a peer's active turn, interrupts late starts, suppresses output and
requests, and only stops a shared process after a failed liveness probe. Frozen v1/v2 fixtures verify migration parity, preserved data and
transactional rollback/retry. No model or API key is required.
