# M7 — Crash recovery and safe restart

Implemented against the expanded M7 specification, pages 67–75 of
[Kru Project Plan and Milestones](Kru_Project_Plan_and_Milestones.pdf).
M7 is implemented in this working tree, targeting the roadmap's v0.2 release.
The current published Git tag remains v0.1.1 until release/versioning is requested.

```sh
bun run demo:recovery
bun run test:recovery:repeat
bun run check:release
```

The demo kills a real daemon process while a scripted native child is running,
then restarts against the same database. It asserts interruption, quarantine,
an explicit missing-usage gap, verified child exit before new provider startup,
queued-successor completion and matching replay projections (fourteen at the
original M7 check; twenty-two after the expanded M6 follow-up). It uses
the actual Codex adapter with a scripted stdio peer and makes no model calls.
Evidence: [macOS](verification/m7-demo-darwin-2026-11-05.json),
[Linux](verification/m7-demo-linux-2026-11-05.json).

## Boot barrier and ownership

The existing daemon lock now includes a random boot epoch. PID, process start
identity and epoch must match; an old heartbeat never permits stealing a live
lock. Host/namespace evidence prevents adopting an unverifiable foreign owner.
Store writes recheck ownership under the writer lock, while provider startup,
turn notifications and tool calls check readiness and the owning execution and
session generation. A stale view cannot enqueue work, finish a batch or release
another batch's lane. A trusted replay of an already committed tool receipt can
return its prior result without repeating the effect.

`Daemon.start()` acquires ownership synchronously, then starts recovery.
Library hosts should `await daemon.ready` before reporting readiness.
Failures reject readiness and close the daemon with `failure` set. No provider
factory or claim runs during recovery. CLI/library enqueues in other Store
connections remain available and stay queued behind the barrier.

Durable boot phases are `inspect → reconcile → contain → verify → ready`.
Any failure records `blocked`. Recovery checks replay parity and lane/turn
invariants before making domain changes. Orphan reservations, mismatched active
members, projection drift and unverifiable cleanup block startup rather than
being silently deleted. A cutoff separates abandoned work from new enqueues.

## Per-execution recovery

`src/boot/recover-execution.ts` uses the existing Store dispatch with a stable
SHA-256 command key derived from the execution/batch id. One execution at a time
commits these facts atomically:

- Every active batch delivery becomes interrupted with
  `daemon_restarted_outcome_unknown`; terminal rows never reopen.
- The durable turn, if one exists, becomes interrupted. A missing native turn id
  stays null. Setup-only claims do not invent a native turn.
- Latest committed scratch items are promoted with source item ids and
  checkpoint sequence/time. Unfinished items retain partial/interrupted flags;
  completed items remain complete. In-memory text after the checkpoint may be lost.
- An uncertain native generation is quarantined and deactivated. An unused
  setup-only binding retains its pending handoff; idle bindings remain available
  for M6 validation after the barrier opens.
- Observed usage is promoted to a partial recovery record, or a missing-usage
  gap is recorded. The old in-flight ledger row is removed without fabricating
  a successful final turn or a final charge.
- The lane reservation is released and promoted scratch is removed.

The normal M4 final transaction wins if it already committed. Recovery leaves
its outcome, items, price snapshot and charge intact. A fault mid-recovery rolls
back the entire batch; another crash after commit resumes cleanup without
duplicate items, gaps or costs. Process ownership is retained in the cleanup
journal independently of lane lifetime.

## Process containment

Daemon ownership files live at
`<database-directory>/processes/<database-id>/`. `--db`/`KRU_DB` and subfolder
invocation therefore select the same database-scoped runtime evidence. The
parent process directory is also checked for legacy unscoped records; sibling
database directories are excluded.

Stock native adapters publish a pre-spawn intent, then record the child PID,
start identity, dedicated process group, host/namespace, database id, owner
epoch/start identity and runtime identity. File publication is atomic and fsynced.
The SQLite journal retains a second durable copy, including membership changes,
so losing an external file cannot hide an old runtime. Normal cleanup records
confirmed containment; a crash leaves restartable pending evidence.

Membership is sampled once a second while the leader identity still matches;
only changes write to disk. Recovery verifies a currently living recorded member
in the original group before signalling. A saved child can establish group
ownership after the leader exits. A reused leader PID never authorises a signal.
If the group is empty, cleanup completes without signalling. Otherwise recovery
sends SIGTERM, waits its bounded grace (default three seconds), revalidates,
escalates to SIGKILL if needed, and confirms no living group member remains.
All waits and OS operations occur outside SQLite transactions.

Malformed/unpublished records, permission failures, foreign host/database
evidence, a live old owner and unrecorded descendants keep recovery blocked.
There is no acknowledgement that bypasses containment. Linux requires readable
`/proc` and `/bin/ps`; macOS uses platform UUID and process start inspection.
Windows containment is unsupported. A descendant that detached or otherwise
escaped verifiable ownership, and external effects, remain outside the guarantee.
Custom provider factories must implement `setProcessScope` if they spawn native
processes; in-process fake clients do not need it.

## Usage gaps and operator workflow

In-flight usage writes keep snapshots, never sums of notifications. The first
observation persists; later observations coalesce over two seconds, with a
periodic flush and an atomic flush at final completion. Scratch output also
checkpoints every two seconds. The checkpoint interval defines the evidence gap.

`recovery_usage` stores the original accounting timestamp, provider/model,
chain set, delivery set, observed tokens and pinned cost estimate, with status
`partial` or `missing`. Unknown/unpriced costs remain null. These records are
separate from ordinary `usage_records` final results. `cost --json` exposes a
separate `recovery` section with observed tokens/partial USD, unpriced entries,
missing executions, unresolved gaps and per-execution chain attribution.
Displayed observations do not bound what the provider actually consumed.

Finite token/USD budgets include durable partial observations and retain holds
for unresolved gaps across midnight, using the original accounting timestamps.
An explicit conservative reserve resolves the accounting hold without asserting
exact usage or retrying the work:

```sh
kru recovery inspect --json
kru status --json
kru log teammate
kru cost --json
kru cost acknowledge <execution-id> --tokens 10000 --usd 1.00 --note "Reviewed effects; conservative reserve"
```

Bounds cannot reduce observed tokens or priced cost and can be recorded once.
The resolution is event-sourced. Acknowledging usage never opens a blocked
process-containment barrier.

After checking partial output, files and any remote effects, explicitly retry
only work you want repeated:

```sh
kru retry <interrupted-delivery-id>
```

Retry creates a new delivery with `retry_of`; the old attempt stays interrupted.
Chain and hop survive, and the usual M5 chain cap applies. It may repeat an edit
or remote action already performed. Boot itself never retries uncertain work.

## Persistence and verification

Migration v8 adds boot/database identity, execution ownership and cleanup
operational tables; session generations and scratch checkpoint sequences; and
three domain projections: `recoveries`, `session_quarantines`, `recovery_usage`.
New version-1 recovery/quarantine/usage/item events preserve shipped payloads
and migrations. This originally brought replay to fourteen tables; expanded
[M6](m6.md) adds migration v9 and brings the current total to twenty-two. Replay
never restores locks or processes. Frozen v7/v8 fixtures cover upgrade, marker
rollback/retry and replay. Current cross-platform regression evidence is in the
[M6 follow-up verification](verification/m6-expanded-2026-11-05.json).

The 24 numbered tests in `test/boot/recovery.test.ts` follow the expanded plan:
real crashes at claim, accepted start, native completion and committed completion;
mid-dispatch rollback; crashes around cleanup; repeated recovery; competing/live
owners; PID reuse; real orphan children; malformed/permission/orphan blockers;
shared runtime bindings; CLI enqueue during the barrier; durable M5 receipts;
partial usage/output; finite-budget holds; epoch fencing; pending handoffs;
manual retry chains; migration/drift; and two-signal shutdown.

Child tests synchronise on persisted state or named checkpoint output before
SIGKILL, with deadlines for failures. They do not use arbitrary pre-kill delays.
All 24 cases pass ten repetitions on macOS arm64 and Linux arm64 in a local
Docker container with an init process and procps. Full strict-type/regression
results and release repetitions are recorded in
[the verification summary](verification/m7-2026-11-05.json).
CI now runs the complete repeated suite on Ubuntu and macOS; no remote CI result
is claimed for these uncommitted changes. Live provider model tests remain opt-in.

## Read-after comparison

After independently implementing recovery, reviewed OpenBot's pinned
[boot-recovery.ts](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/agent/boot-recovery.ts)
alongside Kru's M0 process records, M3 lock and M4 dispatch. The comparison
reinforced distinguishing abandoned from live work and preserving terminal facts.
OpenBot can consult provider history after startup; this expanded Kru M7 spec
requires conservative interruption and containment before providers start.
Kru therefore records uncertainty and replaces quarantined generations, keeping
its own event history authoritative.
