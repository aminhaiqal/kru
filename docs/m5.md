# M5 — Tools and agent-to-agent messages

Implemented from pages 49–50 of the
[Kru project plan](Kru%20%E2%80%94%20Project%20Plan%20%26%20Milestones.pdf).
The daemon registers exactly two Kru tools, `list_agents` and `send_message`,
with opt-in answers, durable call receipts, inherited chains and a default
four-hop limit. Released as the roadmap's v0.1.0.

[M6](m6.md) subsequently adds `history_search` as the third daemon tool and
two thread projections. Tool/projection counts and recorded outputs below
describe the original M5 release.

## Try the deterministic demo

```sh
bun run demo:messaging
```

The script uses a temporary database and two scripted fake teammates. Coder asks
reviewer, ends its first turn, then receives the review in a new turn. It prints:

```text
coder → reviewer → coder: three completed turns, one chain, hops 0 → 1 → 2
Reply requests: false → true → false. No further acknowledgement turn.
Cost: 3 turns, 785 tokens, $0.000000 (deterministic fake).
Replay: 51 events; 9 projections match.
```

[Recorded demo evidence](verification/m5-demo-2026-11-04.json) retains deliveries,
both conversations, cost rows and replay results. No model or credentials are
used. The fake token counts describe this scripted example, not model efficiency.

For real work, create two teammates using your existing provider logins:

```sh
bun run dev -- init
bun run dev -- agent create reviewer --provider claude --model claude-sonnet-5-5 --prompt-profile full
bun run dev -- agent create coder --provider codex
bun run dev -- send coder "Ask reviewer to review the parser change, request a reply, then finish this turn."
bun run dev -- daemon --max-hops 4
```

In another terminal use `log coder --follow`, `log reviewer` and
`cost --by chain`. Native workspace permissions remain configured per agent;
the daemon still declines interactive native approvals. A teammate message
queues work and returns immediately, even when its recipient is paused or busy.

## Tool interface

`list_agents` takes `{}` and returns ids, names, providers and paused flags.
It does not expose instructions, paths, credentials or the full agent config.

```json
{
  "to": ["reviewer"],
  "text": "Review the parser change.",
  "expectsReply": true
}
```

`send_message` accepts `to` (ids or exact names), `text`, optional
`expectsReply`, `laneId` and `inReplyTo`. Defaults are no reply request and the
recipient's main lane. It validates all recipients before writing, rejects
duplicates and self-messaging, and returns the queued message/delivery ids,
effective reply flag, chain id and hop. Unknown arguments and tool names return
clear unsuccessful tool results. The message plus routing header must fit the
existing 32 KiB turn input limit.

For a batch of user messages, the last message supplies the default chain.
`inReplyTo` can select another message in that same active batch. It cannot select
another agent's history or let the model provide its own chain/hop/sender. Agent
and routine deliveries still run alone, preserving M3's request context rule.

The two declarations and static messaging instructions are registered at thread
start/resume. Tool schemas and instructions count toward the existing six-tool
and 8,000-byte limits. Roster changes, message ids, hops and delivery text stay
out of the cached prefix. Provider-native tools selected by a prompt profile
remain separate from Kru's two tools. There is no Kru tool discovery in M5.

Registering these tools changes the configuration fingerprint once when upgrading
from M4. An old binding with a different prefix starts a fresh native session;
its SQLite conversation remains intact. Cross-session/provider handoff is M6 work.

## Ownership, idempotency and cancellation

The scheduler routes calls only through the provider view and confirmed active
thread/turn that own the claimed batch. It derives the sender from that trusted
context. Calls before confirmation, after completion, from another thread or
turn, or after cancellation cannot enqueue messages.

`ToolRouter` imports engine ports. `SqliteToolState` supplies the M4 dispatch
boundary, routing records and reply deduplication. Its receipt key is a bounded
SHA-256 digest of the provider namespace and native thread/turn/call ids. The
input fingerprint includes the owning batch, agent, tool and arguments. A repeat
returns exactly its stored result and appends nothing; changing arguments under
the same call id fails instead of sending again. Enqueue, sender-lane routing
and receipt commit together. A lost/cancelled response can leave a committed
message, so replaying its receipt is essential; it must not resend that message.

Codex retains its native call id. Claude's in-process MCP callback uses its MCP
request id, retaining the distinction between numeric and string ids, rather
than minting a new id for every repeated callback. If no request id is supplied,
the adapter retains its generated-id fallback. Current SDK transport behavior is
covered using a real local MCP connection and scripted SDK messages.

Standalone scheduler hosts opt into tools by injecting `AgentTools`; the daemon
does so by default. Hosts needing durable atomic effects must use a ToolState
backed by the same Store as their mailbox and usage ledger.

## Replies and chain bounds

An agent receiving `expectsReply=true` writes its answer as final assistant text.
After confirmed completion, Kru queues that answer to the original sender's lane
as a new delivery. The answer has `replyTo` set, keeps the chain and increments
the hop, with `expectsReply=false`. It never waits for the sender's next turn.

Sending a tool message back to the current agent sender is treated as a manual
answer. Such an answer is single-recipient, returns to the sender's original
lane, and forces replies off even if the model asks otherwise. Its reply record
prevents a second automatic answer at turn end. A second distinct manual answer
for the same delivery receives an error; transport repeats still return the
original call receipt. New requests to other teammates remain possible.

No automatic answer is generated for failed/interrupted turns or empty final
text. Suppressed replies from confirmed turns retain a reason. Oversized final
answers stay in history and are not forwarded as an unusable delivery.
Unknown turns retain the existing no-automatic-retry rule.

Each outbound delivery increments its source hop; passing `maxHops` produces a
tool error and queues nothing. A request opting into an answer reserves room for
both the request and its answer, so a request at the last available hop is
rejected before the recipient starts. `daemon --max-hops 0` disables outbound
agent messages. The default is 4, configurable by the host or daemon CLI.

An informational/thanks message with replies off can still cause its recipient
to work, but that recipient's final text generates no automatic answer. Repeated
explicit forwarding is stopped by the hop limit. This bounds depth, not fanout
or the total number of tool calls within a turn. Token/USD gates remain per-agent
daily gates, with M4's explicit estimate scope; the hop limit is not an invoice cap.

## Persistence and cost

Migration v5 adds two event-sourced projections without editing v1–v4:

- `message_routes` stores the sender lane for each outgoing message.
- `delivery_replies` records the one sent/suppressed reply decision per incoming
  delivery, including the reply message id or suppression reason.

New version-1 `message.routed` and `delivery.replied` events extend the event
catalog without changing shipped payload shapes. Replay verification now covers
nine projection tables; old M4 databases replay with the two new tables empty.
Old events and cost snapshots remain unchanged. Frozen v4/v5 fixtures cover the
upgrade, row preservation, rollback/retry and the routed request/reply graph.

Automatic reply enqueue, reply/routing events, final answer, usage, every source
delivery's completion and lane release share the end-of-turn dispatch. A failure
in the reply projector rolls them all back. Native tool messages committed earlier
in the turn remain recorded side effects if the turn later fails; they are not
silently rolled back or repeated.

M4 usage records inherit the batch's chain ids. `cost --by chain` therefore
includes the initial user turn and each agent request/answer turn. Shared user
batches retain M4's shared chain-set cost bucket rather than charging their full
cost separately to every root. A single-root A→B→A exchange has three turns in
one bucket, with their input/cache/output counters and estimated dollars.

## Verification

The v0.1 release also closes the plan's pre-release mailbox checks. Migration v6
indexes message-key age; a key expires at original creation plus 30 days only
after every original/retry attempt is final. Enqueue checks its requested key
under the writer lock, and daemon maintenance prunes at most 100 eligible keys
per heartbeat. History remains intact. See [retention decisions](m3-design.md#idempotency-retention-before-v01).

Mailbox storage rejects text over 1 MiB; the existing 32 KiB execution limit
remains separate. New stored provider error strings redact common authorization,
API-key, token, password and credential-URL patterns and are capped at 8 KiB.
This applies before writing turn/delivery events, status or receipt fingerprints;
it does not rewrite historical events or promise to detect arbitrary secrets in
user messages or tool output.

The four numbered tests in `test/messaging.test.ts` match the PDF's Done-when cases:

1. A ends while B is paused; B's later answer creates a new delivery in A's original lane.
2. A/B acknowledgements stop because replies are off on the thanks message.
3. A deliberate forwarding loop reaches the four-hop limit and starts no further turn.
4. The chain cost report contains all turns and exactly their recorded tokens/costs.

Additional tests exercise durable receipts after reopen, conflicting retries,
manual reply deduplication, invalid arguments/ownership, source selection in
batches, reserved reply hops, size limits including context, rollback of an
automatic reply, stable native prefixes, and cancellation with a lost response.
Codex uses the real adapter over a scripted stdio peer; Claude uses the real
adapter/SDK MCP server over an in-memory transport with scripted model messages.
These verify protocol integration without claiming new live model results.

bun run test:messaging:repeat
bun run demo:messaging

## Read-after comparison

After independently implementing the router, reviewed OpenBot's pinned
[tool router](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/agent/openbot-tool-router.ts),
[idempotency helper](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/agent/tool-call-idempotency.ts)
and [delivery formatting](https://github.com/nightly-labs/openbot/blob/0b311bf/src/backend/agent/delivery-content.ts).
The comparison reinforced binding calls to their owning thread, validating the
whole recipient list, preserving a return lane and keeping retry keys bounded.
Kru hashes the complete namespaced identity, keeps return lanes in a separate
projection and commits automatic answers with the source turn. Its roster and
routing context stay out of the stable tool prefix.
